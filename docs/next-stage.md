# 下一阶段：自主接入与可靠接续

2026-09-18 整理。**产品目标已确认；下述分期、接口和命令是待验证方案，尚未实现或排期。** 当前可用操作见 [安装与使用](usage.md)，v1.0 技术事实见 [设计总稿](design.md)。

## 先解决什么问题

用户应能接入自己的一台新设备，知道它是否可用，把当前会话交给它继续，再接回来。重连、配置变化或应用重启后，用户仍能辨认工作归属、实际执行位置和恢复入口。

先保留单用户、每个会话同一时刻一个活动执行端、空闲边界投切。多端登记不等于多端同时写入，也不要求先建设托管云、插件市场或新的桌面客户端。普通工具与模型插件继续使用 DSH 接口；需要改变执行端的工作台才消费 ARC 执行能力。

## v1.0 基线与需要补齐的部分

| 领域 | 当前行为 | 下一阶段要解决的问题 |
|---|---|---|
| 设备登记 | 每个 ARC home 保存一个 `remote.json`；再次 `remote add` 替换它，启动时读取 | 多端点登记、显示和选择，避免修改连接配置就失去原会话入口 |
| 身份 | 执行位置主要表达为 `local / remote`；活动索引范围包含远端配置 | 区分运行环境身份、安装实例、连接地址、原生会话和逻辑会话 |
| 鉴权 | 使用系统 SSH，主机密钥预先确认，非交互认证；私钥不由 ARC 搬运 | 可解释的连接与能力检查，明确授权失败属于哪一层 |
| 投切 | 导出检查点、目标准备并落盘、提交活动索引；Home 和草稿保留 | 配置变化与多端选择后仍可定位同一个接力结果 |
| 恢复 | 区分提交前失败和提交后故障；显式重连，不自动重放 prompt | 确定重复请求、响应丢失、部分完成及重启后的查询与恢复行为 |
| 插件组合 | 核心、ACP 集成、执行 driver 分层；完整 TUI 使用明确标识的扩展版 | 用第二个调用者验证接口可复用，记录版本与能力矩阵 |

## 分层与社区接口边界

| 层 | ARC 的责任 | 优先对照的接口 | 不能直接推定的能力 |
|---|---|---|---|
| 安装与环境 | 保存所连接环境的引用，解释数据归属 | `dsh-distribution` 环境身份与安装实例描述 | 草案不等于已可用的安装或迁移执行器 |
| 连接与能力 | 建立连接、检查能力、处理取消和断连 | `dsh-std` Connection 与能力协商；Fabric 调用边界 | 当前 ACP 扩展不自动兼容这些协议 |
| 原生会话 | 读取、创建、导入所需状态，并保留来源 | SessionCatalog、SessionHistory；待讨论的 SessionImport | 读取历史不等于获准向另一会话任意追加事件 |
| 接力策略 | 逻辑会话、Home、当前端、提交与恢复规则 | ARC 的可选服务与执行接口 | 不把 Home 或信息状态算法强加到公共元协议核心 |
| 工作台 | 选端、状态、提示、用户输入和结果展示 | TUI driver 或后续桌面适配 | 能安装插件不等于能接管执行会话 |

以上公共接口状态以 [2026-09-17 社区调查](research/dsh-community-contribution-2026-09-17.md) 为快照。进入实现前固定所采用 revision，重新核对其类型、能力和贡献规则；缺少的接口先用可复现案例说明，适配保持可选。

## 建议推进顺序与验收出口

### 1. 稳定身份与登记

先明确环境身份、安装实例与连接地址的关系，再设计登记文件和迁移规则。SSH alias、工作区路径和显示名称不能独自承担永久身份；同一设备也可能有多个 runtime 环境。Home 继续表示工作归属，选择新的执行端不能改写它。

验收出口：登记第二个远端不覆盖第一个；识别重复登记与身份不匹配；改名不破坏历史入口；v1 的 `remote.json` 和现有会话有可检查、可恢复的迁移路径。修改地址后重新核验目标身份，不能默默把原会话绑定到另一台机器。

### 2. 可解释的接入检查

分开检查传输可达、SSH 身份、runtime 启动、协议版本、检查点能力、目标工作区。只显示状态和必要的公开标识，不显示私钥或模型密钥。连接成立不代表获得所有工具权限，也不意味着上下文适合交付给该端。

验收出口：缺失能力、版本不匹配或鉴权失败时，在检查点写入目标前拒绝；错误指向可修复的步骤；检查不触发模型调用或业务工具。登记权限与模型、工作区权限分别说明。

### 3. 可靠接续

沿用 v1 的准备与提交边界。重点验证目标准备完成却丢失响应、重复提交、提交前后断连、客户端重启、旧响应迟到等情况。目标导入标识、来源记录、结果回执及持久化去重是候选方案，需要先确定公共接口归属与失败模型。

验收出口：一次用户操作只有一个可判定的活动端；提交前失败保留源端；提交后按已提交目标恢复；结果未知时明确显示待确认状态；不会自动重放 prompt 或历史工具副作用。跨重启保证必须有持久化证据，不能只靠进程内缓存。

### 4. 工作台复用与社区案例

先用 TUI 与无界面调用者验证同一接力能力，再选择一个已有桌面产品做独立适配试验。桌面产品管理插件、交互和本地配置；ARC 提供接入与接续能力。候选产品与限制见 [客户端调查](research/dsh-desktop-plugin-management-2026-09-17.md)。

验收出口：每项兼容声明绑定版本、能力和实测用例；卸载 ARC 后普通 DSH 组合仍可使用；第二个调用者无需复制接力状态机。具备可复现证据后，再按上游规则提交接口反馈或范例收录申请。

## 交互草案

以下只表达操作意图，**不是当前可执行命令或已冻结 API**。命令行和 TUI 应复用同一能力，避免两套设备登记与恢复逻辑。

| 候选命令 | 意图 |
|---|---|
| `/arc add` | 引导登记用户自己的 runtime |
| `/arc list` | 查看已登记目标、连接状态和当前端 |
| `/arc check <target>` | 检查连接、版本、能力和工作区 |
| `/arc auth <target>` | 说明认证方式与状态，提供修复入口；不输出密钥 |
| `/arc switch <target>` | 在空闲边界将当前会话交给指定目标 |
| `/arc remove <target>` | 移除登记；对活动会话的处理规则需先确定，不隐式删除远端数据 |

当前请使用 `dsh-arc remote add` / `remote remove` 配置唯一远端，在 TUI 使用 `/arc status`、`/arc switch`、`/arc reconnect`。完整操作见 [使用文档](usage.md)。

## 后续能力与开放问题

受限子任务委派仍是后续方向：以“本地选定邮件 → 云端公开调研 → 本地回收结果”验证材料范围、授权和审计；它与当前全会话投切不同。信息状态同步独立建立研究基准，不预设摘要或完整历史为唯一算法。

进入编码前需要明确：环境身份复用程度与冲突处理；旧状态迁移及回退；检查点导入的来源与请求身份；响应丢失后的结果查询；删除登记时活动会话的处理。设计取舍按 [沿革记录格式](history.md#后续决策记录格式) 保存。

优先采用确定性本地双 runtime、故障注入和第二调用者验证；真实 SSH、Docker、模型调用按受影响路径补充。当前已通过的测试仍以 [VALIDATION](../VALIDATION.md) 为准，本路线不新增任何验收通过声明。
